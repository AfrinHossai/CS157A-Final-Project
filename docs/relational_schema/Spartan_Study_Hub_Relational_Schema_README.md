# Spartan Study Hub: final relational schema and indexing

This is the physical design for the agreed 14-relation BCNF model, targeting MySQL 8.4 with InnoDB. No SQL statements are included. It specifies the design; it is not an executed database migration.

## Conventions

- Underlined fields are primary-key attributes; PK, FK and UQ mean primary key, foreign key and unique constraint.
- Unlike the conceptual ER diagram, every physical column, including each foreign-key column, is listed explicitly here.
- Every field is NOT NULL except Notification.read_at. A description may be an empty text value if the application permits it.
- All IDs use BIGINT UNSIGNED, including every corresponding foreign key.
- Independent single-column primary IDs are generated by the database. UserCourse and SessionParticipation use composite keys. Notification subtype IDs reuse the parent notification ID.
- All date/time values use DATETIME(6) and are stored in UTC. Creation, join, send and response times are assigned by the backend/database; joined_at is immutable.
- VARCHAR limits are selected application limits. Use utf8mb4 for user-facing text. Normalize email and catalog-code inputs consistently before uniqueness checks.

## Relational schema notation

The schema is written as **Relation(attribute: domain, ...)**. Primary-key attribute names are underlined. Each horizontal table places the attributes across the header and their data types in the next row. These are schema/domain tables, not sample data rows. Foreign-key arrows below each table point from the child field or field set to the referenced parent key.

## Additional integrity rules

- StudySession.ends_at must be later than starts_at.
- SessionParticipation.rsvp_status is restricted to going, tentative or declined. Missing participation means no response. Only current group members may RSVP.
- Resource.resource_type is restricted to notes, link, guide or practice_material.
- Each Notification has exactly one row in exactly one of GroupNotification, MessageNotification or SessionNotification. Create the parent and its one target in one transaction; ordinary foreign keys alone do not enforce this cross-table exclusivity and completeness rule.
- Leadership is derived from GroupMember ordered by joined_at and membership_id within the group; GroupLeader is a view, not a fifteenth base table. Creation and departure procedures prevent an empty surviving group.
- Authorization, RSVP eligibility and membership changes use the agreed transactional procedures. The application account must not bypass them with direct lifecycle-table writes.

## Foreign keys and deletion behavior

CASCADE removes dependent rows. RESTRICT prevents removing a referenced parent until the appropriate cleanup has completed. These are individual referential actions; group deletion and member departure are multi-step application/database routines.

| Child relation and field(s) | Referenced parent and field(s) | On parent deletion |
|---|---|---|
| `Course(department_id)` | `Department(department_id)` | RESTRICT |
| `UserCourse(user_id)` | `User(user_id)` | CASCADE |
| `UserCourse(course_id)` | `Course(course_id)` | RESTRICT |
| `StudyGroup(course_id)` | `Course(course_id)` | RESTRICT |
| `GroupMember(group_id)` | `StudyGroup(group_id)` | CASCADE |
| `GroupMember(user_id)` | `User(user_id)` | RESTRICT |
| `StudySession(group_id)` | `StudyGroup(group_id)` | CASCADE |
| `StudySession(group_id, created_by)` | `GroupMember(group_id, user_id)` | CASCADE |
| `SessionParticipation(session_id)` | `StudySession(session_id)` | CASCADE |
| `SessionParticipation(user_id)` | `User(user_id)` | CASCADE |
| `Resource(course_id)` | `Course(course_id)` | RESTRICT |
| `Resource(uploaded_by)` | `User(user_id)` | RESTRICT |
| `Message(group_id)` | `StudyGroup(group_id)` | CASCADE |
| `Message(sender_id)` | `User(user_id)` | RESTRICT |
| `Notification(recipient_id)` | `User(user_id)` | CASCADE |
| `GroupNotification(notification_id)` | `Notification(notification_id)` | CASCADE |
| `GroupNotification(group_id)` | `StudyGroup(group_id)` | RESTRICT |
| `MessageNotification(notification_id)` | `Notification(notification_id)` | CASCADE |
| `MessageNotification(message_id)` | `Message(message_id)` | RESTRICT |
| `SessionNotification(notification_id)` | `Notification(notification_id)` | CASCADE |
| `SessionNotification(session_id)` | `StudySession(session_id)` | RESTRICT |

Before deleting a message, session, group, or membership that owns sessions, remove affected Notification parent rows first. Their subtype rows cascade from Notification. Then delete the original source. RESTRICT on subtype-to-source references blocks deleting a referenced source while target rows still exist. It does not prevent deleting a target row directly. Atomic notification operations and restricted direct table-write permissions prevent orphan Notification parent rows. Group-wide cleanup follows GroupNotification.group_id, MessageNotification through Message.group_id, and SessionNotification through StudySession.group_id.

For a member departure, also delete their RSVPs in that group and their own group notifications. Deleting their GroupMember row then deletes their sessions and those sessions' RSVPs. If the group becomes empty, delete it. Otherwise the derived leader is the oldest remaining member. Course-scoped resources remain after group deletion.

## Indexing plan

Primary-key and unique indexes are part of the declared keys and should not be duplicated with separate ordinary indexes. Composite indexes below also supply foreign-key index coverage when the FK columns are their leading columns. MySQL requires appropriate indexes for foreign-key enforcement and can create a child index automatically when no suitable one exists; declare the intended indexes explicitly so the design remains clear.

### Primary and unique indexes

Every primary key above has its primary-key index. The additional unique indexes are:

| Relation | Unique index | Purpose |
|---|---|---|
| User | `(email)` | Prevent duplicate login identities and support account lookup. |
| Department | `(department_code)` | Prevent duplicate catalog codes and support department lookup. |
| Course | `(course_code)` | Prevent duplicate course codes; support exact and prefix course-code searches. |
| GroupMember | `(group_id, user_id)` | Prevent duplicate current membership and support the session-creator composite reference. |

### Additional baseline indexes

Column order is intentional. BTREE means an ordinary nonunique B-tree index; FULLTEXT means a word-search index.

| Relation | Indexed fields, in order | Type | Query or operation supported |
|---|---|---|---|
| Course | `(department_id, title, course_id)` | BTREE | Browse one department's courses alphabetically; covers the department foreign key. |
| Course | `(title, description)` | FULLTEXT | Search course titles and descriptions by words. |
| UserCourse | `(course_id, user_id)` | BTREE | Find students who saved a course; covers the course foreign key. |
| StudyGroup | `(course_id, created_at, group_id)` | BTREE | List a course's groups by creation time; covers the course foreign key. |
| GroupMember | `(user_id, group_id)` | BTREE | List a student's groups; covers the user foreign key. |
| GroupMember | `(group_id, joined_at, membership_id)` | BTREE | Find the oldest current member and deterministically break join-time ties. |
| StudySession | `(group_id, starts_at, session_id)` | BTREE | List upcoming sessions for one group in chronological order. |
| StudySession | `(group_id, created_by, session_id)` | BTREE | Supports the composite creator-membership foreign key and departure cleanup. |
| SessionParticipation | `(user_id, session_id)` | BTREE | Find a student's RSVPs; covers the user foreign key. |
| Resource | `(course_id, created_at, resource_id)` | BTREE | List recent resources for a course; covers the course foreign key. |
| Resource | `(uploaded_by, created_at, resource_id)` | BTREE | List a student's uploads; covers the uploader foreign key. |
| Resource | `(title, description)` | FULLTEXT | Search resource titles and descriptions by words. |
| Message | `(group_id, sent_at, message_id)` | BTREE | Read group message history in a stable chronological order. |
| Message | `(sender_id)` | BTREE | Supports sender attribution, ownership lookups and the sender foreign key. |
| Notification | `(recipient_id, created_at, notification_id)` | BTREE | List all notifications for a recipient in chronological order. |
| Notification | `(recipient_id, read_at, created_at, notification_id)` | BTREE | List unread notifications for a recipient, using read_at being absent, then creation order. |
| GroupNotification | `(group_id)` | BTREE | Find all notifications for a source during source or group deletion. |
| MessageNotification | `(message_id)` | BTREE | Find all notifications for a source during source or group deletion. |
| SessionNotification | `(session_id)` | BTREE | Find all notifications for a source during source or group deletion. |

### Optional indexes after measurement

| Relation | Indexed fields | Add when |
|---|---|---|
| SessionParticipation | `(session_id, rsvp_status, user_id)` | filter or count responses by status within a session if measurements justify it. |
| Resource | `(course_id, resource_type, created_at, resource_id)` | accelerate frequent course-and-type filtering while retaining chronological order. |

### Why column order and index choice matter

- UserCourse's primary index (user_id, course_id) already supports one student's saved courses and the user foreign key. The reverse index is needed for efficient course-first access.
- SessionParticipation uses the same pattern: the primary index begins with session_id, while the reverse index begins with user_id.
- (group_id, joined_at, membership_id) supports leadership lookup. A separate group_id-only index is unnecessary because existing membership indexes already begin with group_id.
- Notification needs two recipient-first chronological indexes: read_at sits between recipient and time in the unread index, so that index does not generally provide creation-time order for the all-notifications list.
- The optional course/type resource index does not replace the course/time index for a course-wide chronological list because resource_type intervenes in its ordering.
- An ordinary B-tree does not generally provide an efficient lookup for arbitrary contains searches with a leading wildcard. The FULLTEXT indexes are intended for word-based title/description searches. Course-code exact or prefix searches use the unique course-code index.
- FULLTEXT is not arbitrary substring search; token length, stopwords and language rules affect matches. Searching stored title/description text does not search the contents of uploaded files automatically.
- Do not add standalone indexes on password_hash, read_at, rsvp_status, resource_type, or every description/content column. Their planned access is covered by selective parent-first composite indexes or the designated FULLTEXT indexes.
- The old notification-context unique pairs (group_id, message_id) and (group_id, session_id) are not required in the normalized model. message_id and session_id remain their sources' primary keys.
- Each extra index consumes storage and adds work to inserts, updates and deletes. Use execution plans and representative data to validate the baseline and justify optional additions. Indexing supports the response-time goal but does not by itself guarantee a two-second response.

Checked the metadata for 14 tables and 59 fields: every foreign key points to a declared primary or unique key, corresponding FK types match, and every foreign key has baseline B-tree index coverage in its required column order. This is a design-level consistency check; no MySQL schema or backend has been executed here.
